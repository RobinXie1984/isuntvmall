# Weekly SunTVMall sync

Runs **Mondays at 09:00 Asia/Hong_Kong**, through the Codex heartbeat attached to the owning iSunTVMall chat. No storefront request, daily poll or additional daemon starts a sync. The initial import is the baseline; the first scheduled run is 2026-10-26. Execution requires the iMac Codex host and Studio to be available. An unavailable host/source is a recorded blocker, not a successful sync.

The weekly job is authorized to refresh source product details, variants and prices, stage new products, queue supplier pictures privately, test and deploy. It is **not** authorized to approve new photos, enable payments, change staff access or copy credentials. Routine factual translations and classification are handled by the agent. Source medical/efficacy claims are not automatically copied.

## Existing components reused

- Public Shopify source feed: `https://suntvmall.com/products.json?limit=250`; use ordinary browser download if the public HTTP route is rate limited. Respect gates. For 250 or more items, follow normal pagination and verify completion before comparison.
- `scripts/suntvmall-weekly.mjs`: deterministic change plan, prepared-catalogue validation, audited metadata updates and private image queue.
- Existing Supabase merchandise drafts, revision checks and audit records; existing MUJI batch-originals/processed storage and approval workflow.
- Four-language public catalogue metadata and normal Studio build → verified iMac deployment. Updates require no manual code edits by Robin; the scheduled agent prepares and deploys the data change.

## Run procedure

1. Read current project law and two-machine protocol. Check for concurrent repo changes and prior incomplete runs. Create a new owner-only canonical run folder under `/Users/headlessnick/RobinOS2/12_ventures/isuntvmall/candidates/suntvmall-weekly/YYYY-MM-DD/`. Do not overwrite an earlier run. First baseline: `candidates/20261022-suntvmall-sync/source/products.json`; later baseline: the latest **successfully verified** weekly receipt and archived feed.
2. Download the complete public feed, archive exact bytes, record timestamp/hash/count. Use stable source IDs; never treat a failed/empty/partial feed as product removal. Keep the previous snapshot intact.
3. Run `weeklyPlan(previousFeed,currentFeed,catalogue,date)`. Same feed should produce zero changes. Preserve catalogue array order and append new IDs; retain absent items and report their absence. A no-change run writes its receipt and stops without deployment, database mutations, image uploads or notifications.
4. For changed facts/options, prepare truthful four-language text, preserving pack size, model, colour and variant identity. Use the seven existing categories by actual use. Existing curated wording can stay where the underlying fact is unchanged. Keep source prices subject to the demo-price safeguard below; do not invent numeric stock. New products receive stable source-derived UUID, `SUNTV-{id}`, `suntv-{handle}`, stock zero, is_demo false, status draft and no public image. Any new category requires a useful product-based rationale and four-language labels.
5. Run `validatePreparedCatalogue(previous,next,feed)`. Every source variant ID and policy-adjusted price must match; all translations must exist; existing approved image filename and product identity must remain unchanged. A newly prepared product must have empty `reviewedImageName`. Static metadata must include it **before** any possible publication, keeping the server-side source checkout exclusion effective.
6. Snapshot managed DB rows. Stage new rows as drafts without images; use `merchandise_save` to attach supplier information. For existing rows, obtain `merchandise_list` then call `applyExistingMetadata`. It preserves current publication status, category, supplier and visible image IDs, skips colleague drafts or price conflicts, and uses audited revision-checked save/publish. Do not overwrite conflicts. Do not change stock or enable local checkout. If changing the public metadata, finish the tested build/deploy and compare live prices with selected source variants. On failure retain resumable receipts; never declare a partial run successful or advance the baseline.
7. For new/changed supplier pictures, archive original bytes and hashes in the canonical run. Compare source image ID/URL/version and content hashes; queue only genuinely new/changed files. Allow only public `https://cdn.shopify.com/` media URLs observed in the feed, bounded downloads, known JPEG/PNG/WebP formats and existing byte/admission limits. Unsupported files remain held. Call `queueSupplierPhoto` for the target product; this writes **only** to private `batch-originals` and finalizes for processing. The existing worker normalizes into private `batch-processed` and stops at review. No call to `batch_review`, no auto-approval, no copying to public storage. Byte-derived request IDs prevent duplicate queue entries on retry.
8. Business Super Admin reviews in `/admin/batches`, comparing original/processed images for background clutter, promotions, proportions, product colour, labels and completeness. Approve only a truthful MUJI-quality image. If normalization is insufficient, reject and prepare a reviewed replacement using the existing image workflow. Approval permits the existing worker's public copy; product visibility is then selected in Merchandise. New products remain draft until normal business approval/publication. Existing products keep their approved photo while a replacement is pending. Finance Admin cannot approve merchandise.
9. Verify public images and existing image visibility unchanged by the sync; confirm new products with unapproved imagery are absent publicly. Verify changed price/variant links, preserve colleague edits, run unit tests/typecheck/lint/build where code/data changed, commit/push only task-owned files and retain the exact deployment/build hashes. Archive receipt, original feed, plan, queued batch IDs, changes, conflicts and rollback reference on Studio. Advance baseline only after successful completion; queue admissions still pending are explicitly carried forward.

## Recovery and scope

Keep last known good catalogue/photos when the source is unavailable. Retry only bounded transient failures in that weekly run; do not create a daily retry schedule. Failed runs are reported with the exact blocker. Restore the recorded previous Worker and previous managed price payloads through audited operations if needed; do not delete products or media. No live inventory synchronization or completed payment transaction is claimed: source checkout remains authoritative.

The weekly job uses existing Codex execution, Supabase and Cloudflare access; no new paid service or credential is provisioned. Administrative photo approval remains intentional, even though fetching and commercial-data refresh are automatic.

## Demo-price safeguard — 2026-10-22

Robin authorized HK$999.99 as a clearly labelled demo price when a proper SunTVMall selling price cannot be verified, extending the original footwear correction to all remaining HK$19.99 merchandise. All ten remaining listings were Fourth Meal food/nutrition items. Each live source page repeated HK$19.99 sale / HK$24.99 comparison pricing, with no separately verified intended price. The ten items and earlier nine shoe styles now carry `priceIsPlaceholder` on affected variants. Other source prices and approved photos remain unchanged.

`sourceVariantPrice` maps the source's generic HK$19.99 to HK$999.99 in every category. Preserve this rule during each weekly sync and new-product preparation. Cards and selected variants explicitly identify the amount as a demo price in all four languages. If the source later supplies a different valid price, use it and clear the flag. If HK$19.99 is later independently confirmed as a genuine selling price, document that evidence and introduce a narrowly scoped reviewed exception before publishing it; do not silently bypass the safeguard. Malformed or missing source prices remain held for review.

`validatePreparedCatalogue` enforces both amount and placeholder status; do not bypass it. Supplier checkout is external and unchanged, and buyers must confirm final price there. Local checkout exclusion, product identity, publication status, and the MUJI photo review gate remain unchanged. These are real sourced products with demo prices, not demo-stock records; do not set `is_demo` merely to label a provisional amount.

## Catalogue-wide price disclosure — 2026-10-26

Keep `isDemo` amounts visibly labelled **Demo price · not a selling price** on cards, product pages and any retained cart lines. Do not replace the curated sample prices with supplier offers. The source's 19.99 safeguard still uses 999.99; it is not a rule to replace other valid prices. Normal source amounts are described precisely as **SunTVMall listed price**, with the snapshot date and a reminder to confirm at source checkout. A source-page/feed match verifies what the source lists, not the merchant's intended retail economics, stock or successful payment.

`productPriceDisclosure` checks that a source card's currency and amount match the minimum of its reviewed variant metadata. A conflict keeps the colleague's amount and displays **Price unverified · confirm before buying**. Missing source metadata and malformed or generic 19.99 variant amounts also cannot receive the source-price label. `sourcePriceDisclosure` applies per selected variant, so mixed verified/demo options remain distinct. Keep these labels in English, Traditional Chinese, Simplified Chinese and Japanese.

Do not import source comparison prices or invent discount percentages: the 2026-10-26 audit found 330 variant comparison amounts at or below their selling amounts. Existing legitimate set/model price ranges remain intact. Preserve all approved media, demo flags, stock, source checkout exclusions and the private photo review gate.
