# White-label V1 configuration

## Delivery boundary

This is a reusable storefront and operations template. iSunTVMall is the first white-label demonstration. A second neutral `Stillroom` profile proves local configuration/build independence; it is not a confirmed merchant or a request to provision a new public store. Stripe account setup comes later. A new Supabase project is created only after a real B2B client is confirmed and its setup is authorized.

Use the same application commit with separate public JSON profiles. The selected profile is compiled into the build; it is not selected from a request Host header, URL query or browser setting. One independent deployment/project is the supported customer isolation boundary. A shared multi-tenant database is not implemented.

## Public profile

`config/store-profile-loader.mjs` validates the JSON. `src/lib/store-profile.ts` exposes the compiled profile. Select an arbitrary external JSON file using `STORE_PROFILE_PATH`; client IDs and names are not restricted to the two included examples.

| Field | Purpose |
|---|---|
| `id`, `name`, `origin` | Stable store identifier, visible name and explicit HTTPS origin. Localhost HTTP is permitted for development. |
| `brand` | Local logo/icon asset paths and optional second line with its language. |
| `copy`, `hero` | Explicit English, Traditional Chinese, Simplified Chinese and Japanese public copy; homepage image/navigation. |
| `locales` | Nonempty supported subset of the four implemented languages and a default within that subset. |
| `currency` | `hkd` only in V1. This is not a currency-conversion engine. |
| `catalogueMode` | `demo` for samples; `merchant` for database-backed real merchandise. |
| `demoSet`, `collections` | Select generic or iSun samples and explicitly enable supplier/holiday demonstrations. Merchant mode rejects enabled demo collection switches. |
| `excludedProductIds` | Exact public exclusions. Admin and audit records remain available; no database records are deleted. |
| `policies` | Supplied merchant identity/contact and shipping/returns/privacy/terms text. Unknown values stay null. |
| `indexing` | Whether the build advertises index or noindex to crawlers; not a claim about actual indexing. |

Logo/hero/icon references point to files under `public/`. A new deployment must carry the referenced files as well as its profile. Profile content is public: never put credentials, private staff records, wholesale prices or source documents into it. Unknown keys are rejected. Plain policy text is rendered as text, not HTML.

The default profile preserves the existing iSun comet, bilingual lockup, MUJI composition, four languages and browser cart/locale/staff namespaces. Other IDs receive distinct stable namespaces. Do not change an active store ID casually. New MFA enrollments use the selected brand issuer; existing factors are not rewritten.

## Catalogue behavior

Demo mode retains the first store's examples. The neutral proof selects a small set of generic sample goods without the supplier collection or holiday routes. Merchant mode has no bundled-product overlay, guessed demo-slug fallback, fictional host fallback or preview-room fallback. If no database is configured, it returns an empty catalogue rather than substituting samples. Public database merchandise marked `is_demo` is filtered out.

The verified iSun workflow QA product is excluded by exact ID from public listing, detail, cart and live product rails. Public polling applies the same exclusion after the database public-room RPC and clears any hidden pin. This does not delete the QA record or weaken the RPC's active-host/public-room checks.

Purchase-information, privacy, terms and contact pages show provided text. Null values render an honest “not provided yet” message. Do not invent an actual merchant, address, support email, shipping fee, delivery guarantee or return period. Presence of text is not legal approval or payment readiness.

## Public build selection versus private runtime settings

| Kind | Settings | Handling |
|---|---|---|
| Public build input | `STORE_PROFILE_PATH` | Path to validated public JSON. Optional; defaults to iSunTVMall. |
| Internal serialized public build value | `NEXT_PUBLIC_STORE_PROFILE` | Generated by both build configurations. Do not set manually. Contains public profile only. |
| Deployment origin | `NEXT_PUBLIC_SITE_URL` | Runtime origin for authorization/redirect checks; must agree with the intended profile/domain. |
| Database server | `SUPABASE_URL`, `SUPABASE_SECRET_KEY` or legacy `SUPABASE_SERVICE_ROLE_KEY` | Separate confirmed-client project credentials. Secret stays in server configuration. |
| Staff identity | `SUPABASE_PUBLISHABLE_KEY` | Server-side Auth setup; a publishable key is not a staff role. |
| Batch capability | `BATCH_HELPER_ENABLED` | Enable only after storage, migrations, named accounts and worker verification. |
| Future payments | `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_ACCOUNT_ID`, `STRIPE_MODE`, optional `STRIPE_SHIPPING_RATE_ID`, `STRIPE_ALLOWED_SHIPPING_COUNTRIES`, `STRIPE_AUTOMATIC_TAX` | Configure later with the confirmed merchant. Flags or keys alone are not acceptance evidence. |
| Abuse protection | `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `CHECKOUT_CLIENT_HASH_SECRET` | Separate public widget key and private server secrets. Do not reuse another merchant's credentials. |
| Sale-release gate | `CHECKOUT_RELEASE_APPROVED` | Keep unset/false until merchant policies, independent credentials and acceptance are complete. Demo profiles remain closed. |
| Maintenance | `COMMERCE_MAINTENANCE_ENABLED` | Leave inactive until the actual project and worker scope are approved. |

Worker account/name/routes, runtime secrets and deployment targets are separate from the profile. No new Stripe account, client database or external sample store is part of this template-first configuration work. The payment/runtime owner maintains any additional activation flags; see its current release documentation before activation.

## Reproducible checks

From the repository root with its pinned dependencies installed:

```sh
npm run test:run
npm run typecheck
npm run build:vinext
```

For the neutral proof, use a separate task-owned build directory so its output cannot replace the iSun deployment artifact:

```sh
node scripts/prepare-store-deployment.mjs --profile /absolute/path/to/config/stillroom.json --target /absolute/path/to/target.json --out /task-owned/path/wrangler.json
STORE_PROFILE_PATH=/absolute/path/to/config/stillroom.json STORE_DEPLOYMENT_CONFIG=/task-owned/path/wrangler.json npm run build:vinext
```

The same method accepts a confirmed client's external profile. Next builds also load the selected profile through `next.config.ts`. Builds are not deployments. Do not run a deploy command from the neutral output against the existing iSun Worker configuration.

Focused coverage includes `store-profile.test.ts`, `data/store-profile-isolation.test.ts` and `live/store-visibility.test.ts`. They cover schema rejection, arbitrary valid client IDs, language defaults, namespaces, absent-database merchant behavior, demo exclusions, exact QA preservation and polling-pin filtering. Actual test/build pass counts, browser evidence and deployed versions belong in the release receipt; this document does not claim they have run successfully.

## Deployment-target preparation

`config/deployment-target.example.json` is a non-deployable example with a zero account ID and reserved example hostname. Supply a confirmed target containing only `profileId`, namespaced `workerName`, `accountId`, `origin`, `customDomain` and (only for a custom domain) `zoneId`. The target must exactly match the selected profile ID/origin. No secret fields are accepted.

`prepare-store-deployment.mjs` creates a new configuration and SHA-256 receipt, refuses existing outputs and never deploys. Vite requires this explicit configuration for any non-default store, verifies the profile/config hashes, and refuses accidental use of the iSun production identity. The default iSun build continues using its existing `wrangler.jsonc` unchanged. Editing the profile or generated config invalidates the receipt; generate a fresh task-owned output.

Run `node --test scripts/prepare-store-deployment.test.mjs` for target separation, tamper/mismatch and no-overwrite checks. These are local tests; a generated file is not provider access or deployment approval.
